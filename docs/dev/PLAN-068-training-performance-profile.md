# PLAN-068：训练性能分解与瓶颈调查

日期：2026-10-26

基准代码：`a924b1fabf34f9064b0523f858f7b4a87f9b82e5`。

## 用户目标

用户希望先通过 profile 统计真实耗时、调查 nnlearn 相对 PyTorch 的差距，再进行有针对性的优化。本任务先交付可复现测量和有证据的优先级，不修改库的训练语义或开始重写 CUDA 后端。

## 调查范围

1. 复现 `examples/704_compat_training_performance_benchmark.py` 的小型 MLP，并使用较大 MLP 区分框架开销与计算规模的影响。
2. 固定共享输入、初始参数、float32、梯度需求、优化器、CPU 线程数与 CUDA 精度设置；记录软件、硬件、线程池及环境变量。
3. 先验证前向、损失、所有参数梯度及连续参数更新的一致性，再计时；CPU 和 CUDA 串行运行，避免相互干扰。
4. 不加 profiler 的端到端训练时间作为性能基准；分别统计清梯度、模型前向、损失、反向、优化器更新。CUDA 明确区分主机耗时、stream 经过时间和 GPU 实际活动时间。
5. 保存 CPU cProfile 的独占/累计时间及调用次数；使用可用的 CUPTI/时间线工具统计 CUDA kernel、拷贝、同步与空闲间隔，先验证工具确实捕获 CuPy 活动。
6. 对关键路径补充不改变计算结果的调用计数和有限的对照实验，评估通用矩阵乘法封装、GPU 标量处理、未请求输入梯度仍被计算等候选因素。对照实验仅在调查进程内生效，不改库实现。
7. 如调查显示空间算子具有独立瓶颈，补充卷积/池化的有限工作负载测量；明确结论适用范围。

## 实施步骤

1. 增加独立诊断脚本，沿用项目 Python/uv 和现有 argparse 使用方式；原始基准与 profiling 分开运行。
2. 按固定配置运行 CPU/CUDA 测量，保存机器可读的结果、调用统计和时间线摘要。大型 trace 留在本地，文档记录重建命令及位置。
3. 根据实测数据形成调查报告，区分已证实原因、待验证假设、测量干扰和适用边界，并列出后续优化顺序与验收标准。
4. 自查脚本、核对时间口径及原始数据，执行相关验证和静态检查，生成结果文件并更新 `docs/dev/INDEX.md`。
5. 使用中文提交，提交消息逐项列出计划、结果、调查报告与变更；提交后立即推送。

## 验收标准

- 不使用带 profiler 的耗时作为与 PyTorch 的性能倍数；不将累计时间重复相加，也不把 CUDA event 区间当作纯 kernel 执行时间。
- 基准包含多次重复、原始值及统计离散度；记录实际步骤、预热与设备同步边界。
- CUDA 分析明确说明是否实际捕获 CuPy kernel/拷贝，缺失时不得将缺失数据解释成零开销。
- 结果能追溯到命令、配置、代码版本、原始数据及源码位置；后续优化建议有测量依据。
- 库文件保持原有实现；诊断脚本完成真实 CPU/CUDA 运行及数值核对。

## 计划自查

1. 本轮针对已观察到的小 MLP 差距，较大 MLP用于检验规模影响，不能由此推断所有 CNN/Transformer 性能。
2. 分阶段同步会改变调度，采用独立测量并披露开销；GPU 时间线与 cProfile 的耗时只用于归因。
3. 性能实验不并行运行；保持用户已经授权的自动提交与推送配置。

## 调查中调整

- 首轮 200 步的小 MLP CPU 对照有较大离散度，补充 1000 步、100 步预热、7 次重复的独立长采样；完整保留首轮数据，不以单轮结果定论。
- 调用统计确认每步执行 6 次 MatMul，源码显示第一层仍计算不需要的输入梯度。增加仅对二维矩阵生效的临时对照，并重新核对全部参数梯度和连续更新。
- 扩展对照出现显著离群值；系统观察到其他 GPU 进程及高 I/O 压力。补充固定当前测量进程 CPU 亲和性、单线程的运行，记录训练区间进程/主线程 CPU 时间、资源计数及区间外系统快照；进程 CPU 时钟的 cProfile 与墙钟 cProfile 分开保存。其他进程保持原状，不能声称已取得独占 GPU 环境。
